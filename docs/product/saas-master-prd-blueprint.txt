
KRUZE ENTERPRISE MOBILITY OS
Master Product Requirements Document (PRD) + SaaS Architecture + Technical Build Blueprint
Purpose: This document is intended to be sufficiently detailed for an engineering team or coding agent to begin system design, database design, API contracts, UI implementation, and phased development without relying on the earlier conversation.
Core product principle: The platform plans, assigns, optimizes, executes and monitors employee transportation automatically. Humans manage exceptions.
Document status: Build baseline v1.0 | September 2026
1. Product Definition
Kruze is a multi-tenant, multi-organisation, relationship-aware SaaS platform for enterprise employee transportation, fleet operations, vendor management, driver/vehicle compliance, routing, safety, trip execution, commercial reconciliation and analytics.
It must support two primary go-to-market models simultaneously:
Model
SaaS Customer / Account Owner
Downstream Access
Corporate-led
Corporate uses Kruze directly
Corporate onboards multiple fleet operators/vendors; vendors manage drivers, vehicles and guards.
Operator-led
Fleet Operator or Vendor uses Kruze as its technology platform
Operator onboards corporate customers and manages fleet, drivers and day-to-day transport operations; each corporate receives a restricted corporate portal.
Kruze remains the platform authority in both models. The organisation that brings a corporate can become its Operating Partner, but the corporate retains its corporate tenant/data context and can later connect additional vendors if its plan/permissions allow.
2. Non-Negotiable Architecture Principles
One Kruze platform, not separate corporate and fleet products.
Every major real-world entity has one global Kruze identity; do not duplicate a driver or vehicle merely because it participates in multiple organisations.
Organisations and resources are connected through explicit relationship/assignment records, not rigid foreign-key ownership alone.
RBAC alone is insufficient: authorization must combine RBAC, relationship context and attributes (organisation, corporate, city, contract, trip, resource ownership and assignment).
Tenant isolation must be enforced server-side on every query and mutation.
Supervisor is an exception manager; normal transport planning is automated.
Safety, compliance and contract constraints are hard constraints in planning/allocation where configured.
Every operational override must be auditable.
Corporate employee/HR data must not automatically become visible to a vendor beyond fields required to execute assigned transport.
Vendor/fleet resources not assigned to a corporate must remain invisible to that corporate.
Support/admin impersonation must be explicit, time-bound, reason-coded and fully audited.

7. Automated Daily Operating Flow
1. HRMS/API/CSV supplies employees, shifts, attendance/leave and roster changes.2. Roster Engine determines eligible transport demand.3. Planning Engine groups employees by shift, geography, office and constraints.4. Relationship Engine identifies authorized vendors/operators/resources.5. Compliance Engine filters non-compliant drivers/vehicles/guards/vendors.6. Allocation Engine assigns vendor + vehicle + driver + guard.7. Route Engine optimizes pickup/drop sequence and ETA.8. Safety Engine validates female/last-drop/escort/night/geofence constraints.9. Cost Engine estimates trip cost.10. Plan is generated with exceptions.11. Supervisor reviews only unresolved exceptions or configured approval items.12. Plan is published.13. Driver, employee, guard and vendor receive assignments.14. Live execution uses GPS + pickup OTP + drop OTP.15. Live optimizer reacts to cancellations, traffic, breakdowns and resource changes.16. Completed trip is validated against GPS/OTP/events.17. SLA, billing, vendor payable, analytics and audit records are generated.

9. Trip State Machine
CREATED → SCHEDULED → RESOURCES_ASSIGNED → DRIVER_ACCEPTED → EN_ROUTE_TO_FIRST_PICKUP → ARRIVED_AT_STOP → EMPLOYEE_PICKED_UP → RUNNING → EMPLOYEE_DROPPED → COMPLETEDAlternate terminal/intermediate states:CANCELLED | NO_SHOW | BREAKDOWN | SOS_ACTIVE | PAUSED | REASSIGNING | FAILED
Every state transition must emit a domain event and audit record. Invalid transitions must be rejected server-side.
10. OTP & Proof-of-Service Specification
Generate cryptographically secure short-lived OTPs; never store plaintext OTP if avoidable—store a one-way verification representation.
Pickup and drop OTP must be distinct.
Bind OTP to employee + trip + stop + purpose + validity window.
Driver app submits OTP; backend validates authorization and trip state.
Where policy requires, validate vehicle/driver assignment, time window and GPS/geofence.
Limit attempts and rate-limit verification.
Support controlled fallback: supervisor-authorized manual verification with reason and audit.
OTP success creates immutable trip event with timestamp and location.
Reassignment invalidates or regenerates OTP context as appropriate.
Never expose another employee's OTP to drivers before the relevant stop beyond the minimum required UI.
11. Safety & Last-Drop Rules
Do not hard-code a single gender rule. Build a configurable policy engine because corporate and jurisdictional requirements differ.
Rule Example
Action
Night trip + female employee + policy forbids female final passenger
Optimizer must reject route where that employee becomes final passenger and find a compliant sequence.
Escort mandatory after configured time
Trip cannot publish without eligible guard unless authorized exception policy exists.
Unexpected stop > threshold
Create safety event; notify control room; escalate based on severity.
Route deviation > threshold
Warn driver/control room; recalculate ETA; escalate if persistent.
GPS unavailable
Create tracking-health event; apply configured escalation.
Overspeed
Create safety event with threshold and duration.
All safety policy evaluation results should be stored with policy version, input context and outcome so a later audit can explain why a route was accepted or rejected.
12. Multi-Organisation Driver & Vehicle Rules
Driver is a global identity; vendor relationship determines which vendor may manage/assign the driver.
A driver may have multiple active vendor relationships if allowed.
A vendor must only see the driver's data needed for its relationship and assignments.
Corporate sees driver/vehicle details only for resources eligible/assigned to that corporate.
Global driver availability must prevent conflicting assignments across vendors where Kruze has visibility of both.
Compliance is evaluated as global base requirements + vendor requirements + corporate requirements + trip-specific requirements.
Vehicle follows the same global-identity and relationship model.
Assignment history must be time-bound; never overwrite history when a relationship changes.

Recommended starting architecture: modular monolith with clear domain boundaries and an event-driven internal design. Extract high-throughput services later.

14.1 Suggested Backend Modules
/auth/identity/tenant/organisation/relationship/corporate/employee/hrms/shift/roster/vendor/fleet/driver/guard/contract/compliance/policy/planning/routing/allocation/trip/otp/tracking/safety/incident/notification/billing/invoice/sla/analytics/integration/subscription/audit
14.2 API Conventions
REST for core CRUD/commands initially; version APIs (/v1).
Use opaque UUID/ULID internal identifiers; human-readable Kruze IDs are display/reference IDs, not authorization boundaries.
All requests derive authenticated user, active organisation context and allowed relationship scope server-side.
Use idempotency keys for booking, trip generation, assignment, billing and external webhook commands.
Use optimistic concurrency/version columns for rosters, routes, policies, contracts and trip mutations.
Return machine-readable error codes (e.g., COMPLIANCE_BLOCKED, RELATIONSHIP_NOT_AUTHORIZED, DRIVER_CONFLICT).
Publish domain events after committed state changes using an outbox pattern.
Webhooks should be signed, replay-protected and retryable.
15. GPS / Real-Time Architecture
Vehicle GPS / Driver App       ↓Ingestion Gateway (HTTP/MQTT/provider adapters)       ↓Validation + Device/Trip Resolution       ↓Event Stream       ↓Tracking Processor       ├─ current location cache       ├─ trip location history       ├─ geofence events       ├─ route deviation       ├─ ETA updates       └─ safety events       ↓WebSocket / SSE       ↓Control Room + Employee App

17. Security Requirements
Target enterprise-grade security and independently verified penetration testing; do not market the system as 'foolproof'.
OWASP ASVS-aligned secure SDLC and application controls.
MFA for privileged users; SSO/SAML/OIDC for enterprise.
TLS in transit and strong encryption at rest.
Managed KMS/secrets vault; no secrets in code or client apps.
Strict server-side tenant/relationship authorization on every object.
PII minimization and field-level masking in vendor/driver views.
Signed/short-lived file access URLs; malware scanning for uploads.
Rate limiting, WAF, bot/abuse controls and DDoS protection.
Secure session/token rotation and revocation.
Centralized security logs and alerting/SIEM integration.
Encrypted backups, tested restore, DR/BCP.
Dependency/SAST/DAST/container/IaC scanning in CI/CD.
Independent web/API/mobile penetration testing before enterprise GA and after major security-sensitive releases.
Audit sensitive exports and bulk downloads.
Data retention/deletion/consent workflows aligned to applicable privacy obligations and customer contracts.
17.1 Mandatory Pentest Scenarios
Corporate A attempts to access Corporate B employee/trip.
Vendor A attempts to access Vendor B fleet/driver.
Fleet Operator attempts to access a corporate it does not manage.
Driver attempts to access another driver's trip.
Corporate attempts to edit vendor-owned driver master data without permission.
IDOR/BOLA across every object ID.
Privilege escalation between employee/driver/supervisor/admin roles.
OTP brute force/replay/cross-trip reuse.
GPS spoofing/tampering scenarios.
File upload abuse, injection, SSRF, broken authentication, JWT/session flaws, mass assignment and race conditions.
Support impersonation abuse and audit bypass.
18. Privacy & Data Segmentation
Corporate owns its employee transport data context.
Vendor/operator owns/manages its resource master data subject to contractual/platform terms.
Trip records are shared only with parties participating in that trip and permitted roles.
Employee phone/home location should be exposed to driver/vendor only to the minimum extent required for trip execution and according to policy.
Location data retention must be configurable and documented.
Closed vendor relationships must remove future access while preserving legally/contractually required historical audit records.
Data export and deletion must be scoped to tenant and relationship rights.

23.3 Driver Works with Multiple Vendors
Global Driver Rahul→ Vendor A relationship ACTIVE→ Vendor B relationship ACTIVE→ global availability/conflict engine→ Corporate eligibility evaluated per relationship→ Driver app shows all of Rahul's authorized assignments→ Vendor A sees only Vendor A context→ Vendor B sees only Vendor B context
23.4 Automated Plan
Roster cutoff reached→ demand snapshot→ eligible vendor/resource pool→ compliance filtering→ route grouping/optimization→ resource allocation→ safety validation→ guard assignment→ cost estimate→ exceptions→ publish
23.5 Live Re-optimization
Cancellation / traffic / breakdown / driver unavailable / new booking→ identify affected trips→ lock current execution-safe state→ calculate feasible alternatives→ safety + compliance validation→ apply automatically if policy allows OR raise approval exception→ regenerate ETA/assignment/OTP context→ notify affected parties→ audit
24. Billing & Commercial Model
The billing engine must distinguish SaaS billing (Kruze subscription) from transport commercial billing (Corporate ↔ Vendor/Fleet Operator).
Kruze SaaS: plan, active employees, vehicles, trips, modules, API/SSO/enterprise features or negotiated enterprise contract.
Transport billing: per KM, per trip, per vehicle, per shift, per employee, fixed monthly, minimum guarantee, hybrid.
Rate cards must be versioned by effective dates.
Validated GPS/approved distance and trip completion evidence feed reconciliation.
Support corporate charge, vendor payable, penalty, allowance, tax and adjustment as separate ledger components.
Never overwrite recalculated historical commercial results without version/audit.

28. Coding Standards / Engineering Guardrails
Domain-driven module boundaries; avoid direct cross-module DB writes.
Use database transactions for critical state changes.
Outbox pattern for reliable domain events.
Idempotent commands for external/retry-prone operations.
Soft delete only where appropriate; use explicit lifecycle status and history for auditable business records.
UTC timestamps in storage; render in organisation/local timezone.
Never authorize based on client-supplied tenant/vendor/corporate IDs alone.
Schema migrations are mandatory and version-controlled.
Automated unit, integration, authorization and end-to-end tests.
Feature flags for risky/new enterprise modules.
Structured logs with correlation IDs; never log OTPs, tokens or unnecessary PII.
Secrets only from managed secret stores.
API contracts documented via OpenAPI.
Background jobs must be retryable, observable and dead-lettered after configured failures.

34. Final Product Statement
Kruze is an Enterprise Employee Mobility & Fleet Operating System. It provides one SaaS technology layer for Corporates, Fleet Operators, Vendors, Drivers, Vehicles, Guards and Employees. A Fleet Operator or Vendor can use Kruze as its own technology solution and onboard corporate customers; a Corporate can use Kruze directly and onboard multiple vendors. Vendors/operators manage their drivers and fleet, while corporates manage employees, transport demand, policies, SLA and oversight. Global identities and relationship-based permissions allow the same driver, vehicle or vendor to participate in multiple authorized corporate ecosystems without duplicate accounts or data leakage.
The product's operating principle is: if the system has enough authorized information to make a safe, compliant decision according to policy, it should make that decision automatically. Supervisors manage exceptions.
