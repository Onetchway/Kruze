1. Executive Product Definition
Kruze is a multi-tenant, multi-organisation employee transportation and fleet operating system. It is not a simple fleet tracker. It is the technology layer connecting corporates, fleet operators, transport vendors, employees, drivers, guards, vehicles, supervisors, finance and compliance teams.
Core operating principle: if Kruze has enough trusted information to make a safe policy-compliant decision, it should make the decision automatically. Supervisors primarily handle exceptions, approvals and emergencies.
A Fleet Operator or Vendor can use Kruze as its technology platform and onboard corporate customers.
A Corporate can subscribe directly to Kruze and onboard multiple fleet operators/vendors.
A Fleet Operator/Vendor that onboards a Corporate manages the fleet, drivers, guards and daily execution for that relationship.
A Corporate remains the owner of its employee transport program, employees, shifts, rosters, policies, approvals, SLA and reporting.
One Vendor can serve many Corporates; one Corporate can use many Vendors.
One Driver can have relationships with multiple Vendors and may serve multiple Corporates, without duplicate Kruze identities.
Kruze remains platform authority for identity, tenancy, security, subscription, global audit and platform governance.

5. Authorization Model
RBAC alone is insufficient. Implement RBAC + relationship-based access + attribute/policy checks.
authorize(user, action, resource, context):  verify authenticated identity  verify active organisation membership  verify role permission  verify tenant/organisation relationship  verify corporate/vendor relationship where applicable  verify resource authorization/assignment  verify city/site/department attributes  verify contract/policy status  return ALLOW or DENYNever authorize only by resource ID.
Scopes: platform, organisation, corporate, vendor, city, site, department, contract, trip.
Support break-glass/impersonation must be reason-based, time-limited and fully audited.
All manual overrides require actor, reason, before/after value and timestamp.

10. Safety Rules
Safety must be configurable and should not encode one universal gender/drop rule. Employer policy, applicable law and operating context determine the rule. When configured as mandatory, the optimizer treats it as a hard constraint.

11. OTP & Proof-of-Service
Generate independent pickup and drop challenges per employee per trip.
Store only a secure hash of OTP; never store plaintext OTP in long-lived logs.
Bind OTP verification to trip, employee, assignment version and time window.
Validate geofence/location when policy requires it.
Rate-limit attempts and lock/escalate after configurable failures.
Support supervisor override only with permission, reason and audit.
Create immutable boarding/drop event containing timestamp, location, actor/device reference and verification method.
Design a policy-controlled offline fallback for low-connectivity operations; reconcile server-side once online.

18. GPS / Tracking Architecture
GPS Device / Driver App        |        vTracking ingestion endpoint / IoT gateway        |        vEvent stream        |        +--> latest-location cache        +--> durable location storage        +--> ETA / route-deviation processor        +--> safety-event processor        +--> WebSocket/SSE live control room
Do not write every GPS ping through the ordinary transactional request path.
Apply retention/downsampling policy for raw location history.
Capture accuracy, source and timestamp; protect against impossible/stale points.
Treat GPS spoofing detection as a risk signal, not a perfect guarantee.

MapProvider:  geocode()  reverseGeocode()  distanceMatrix()  directions()  eta()  snapToRoad()  trafficAwareRoute()

20. Security Requirements
Enterprise SSO via OIDC/SAML, MFA, secure session management and device/session revocation.
Argon2id/bcrypt-class password hashing if passwords are supported; never store plaintext credentials.
TLS in transit; encryption at rest; KMS-managed keys; secrets manager; key rotation.
Strict tenant/relationship authorization on every data access path.
PII minimization, masking, retention and deletion workflows.
Signed/short-lived object-storage access; malware scanning for uploads.
WAF, rate limiting, abuse controls and DDoS protections.
CSRF protection where cookie auth is used; secure headers; CSP.
Central audit/security logs; alerting for privileged actions.
Backups, tested restore, disaster recovery and business continuity.
Secure SDLC: SAST, dependency scanning, secret scanning, IaC scanning, DAST and release gates.
Independent VAPT for web, API, employee app, driver app, guard app and cloud configuration.
Threat modeling for tenant isolation, OTP abuse, GPS spoofing, account takeover, privilege escalation and business-logic abuse.
Use OWASP ASVS as a web/application security verification baseline and OWASP API Security guidance for API testing. Security should be verified continuously; do not market the system as 'foolproof'.
21. Privacy & Data Governance
Separate operational necessity from optional analytics/marketing processing.
Define controller/processor roles contractually per deployment.
Purpose limitation for employee location and emergency information.
Configurable retention for GPS, trip history, documents and audit data.
Data subject request workflow where legally applicable.
Consent/notice and lawful processing configuration should be reviewed for each market.
Data residency and subprocessor inventory for enterprise customers.
Do not expose full personal documents to corporate users when a compliance status is sufficient.

28. Critical Test Scenarios
Vendor A cannot access Vendor B's unrelated drivers, vehicles or trips.
Corporate A cannot access Corporate B employee or trip data.
Fleet Operator sees only corporates connected through active relationships.
A driver with two vendors sees only his own assignments, with correct vendor/corporate context.
Driver cannot be double-booked across vendors for overlapping trips.
Expired compliance blocks auto assignment.
Mandatory guard rule prevents plan publication without eligible guard.
Configured last-drop safety rule causes optimizer to reject violating route.
Employee cancellation causes correct capacity/route re-evaluation.
Breakdown finds eligible replacement without leaking unrelated vendor resources.
Pickup OTP cannot be reused for drop or another trip.
OTP brute-force attempts are throttled/locked.
GPS/geofence policy rejects/flags impossible proof-of-service where configured.
Published plan cannot be silently overwritten; new version is created.
Manual override records actor, reason and before/after.
Corporate terminating Vendor A preserves historical trips while preventing new assignments.
Adding Vendor B to same Corporate enables only contract-authorized resources.
Invoice reconciliation uses validated trip context/rate-card version.

31. Final Product Principle
Kruze is one shared technology platform with independent organisations and a relationship-driven permission model. A Fleet Operator/Vendor can onboard and operate Corporate customers; a Corporate can directly use Kruze and add multiple Vendors; Vendors manage their own fleet, drivers and guards; drivers can have multiple vendor relationships; all trip execution is bound to an explicit corporate/vendor/contract context.
The daily operating objective is automation: roster -> demand -> optimized routes -> vendor/vehicle/driver/guard allocation -> compliance/safety validation -> publish -> live execution -> OTP proof -> SLA/billing/analytics. Humans manage exceptions, approvals and emergencies.
